# B1 — The Glacier cost gotcha

## The actual cost impact

`storage_class = "GLACIER"` is S3 Glacier Flexible Retrieval, which has a **90-day minimum storage
duration**. Deleting (or overwriting/transitioning) an object before that is not free: S3 bills a
**pro-rated early-deletion charge for the days remaining**, as if the object had stayed.

Timeline from the scenario:

| Day | Event | Billing |
|---|---|---|
| 0 | Upload | S3 Standard |
| 30 | Lifecycle moves it to Glacier | Transition request fee; Glacier clock starts |
| 40 | Seller requests deletion; we delete immediately | 10 days actually stored in Glacier |
| — | Early-deletion charge | Remaining 80 days of the 90-day minimum are billed anyway |

So the delete saves **nothing** on the Glacier side for 80 days. The object is billed as if it lived
until day 120. Also paid regardless of deletion: the per-request transition fee (priced per 1,000
requests) and the metadata overhead Glacier adds per object (about 40 KB: 8 KB charged at Standard
rates and 32 KB at Glacier rates). For small photo files the overhead can be a large share of what
was "saved" by archiving.

Rough scale (US East list prices, check current pricing): about $0.0036 per GB-month, so an early
delete costs roughly 80/30 x $0.0036 = about **$0.01 per GB**. Small per object, but it scales with
deletion volume (about $100 per 10 TB deleted early), and it never shows up in a storage forecast
that assumes "deleted = no longer billed". That is why it quietly runs over budget: it appears as
`EarlyDelete-ByteHrs` usage, not as normal storage.

It is also not a one-off: every photo that is deleted between day 30 and day 120 pays this. Since
we move **every** sold listing at day 30 but deletion requests can arrive at any time, a steady
share of objects will land in that window.

## Redesign

1. **Stop archiving objects that are likely to be deleted soon.** Move the transition from 30 days
   to at least 90 to 120 days after upload (or after the listing is marked sold), so by the time
   an object enters Glacier, the minimum-duration clock rarely overlaps with a deletion request.
2. **Or use a class without a minimum.** `INTELLIGENT_TIERING` has no minimum storage duration and
   no early-deletion fee (it adds a small per-object monitoring fee; objects under 128 KB are not
   monitored or tiered, which suits tiny files). For photos that may be deleted at any time, this
   removes the penalty by design. Note `GLACIER_IR` also has a 90-day minimum, and Deep Archive 180.
3. **Use the deletion SLA.** Deletion must complete within 30 days of the request, so do not
   delete immediately. Make the object **inaccessible right away** (delete marker / revoke access /
   remove from the listing), then schedule the physical delete at the **end of the SLA window or the
   end of the 90-day minimum, whichever comes first**. For a request made on day 90 or later this
   reaches day 120 inside the SLA and the fee disappears; for earlier requests it still cuts the
   charge. This needs a small scheduled job (Step Functions or EventBridge + Lambda); S3 lifecycle
   expiration counts from object creation, not from a tag, so it cannot do this alone.
4. **Make it visible.** Tag every object with `landlord_account_id` (the billing unit), alert on
   `EarlyDelete-ByteHrs` usage with an AWS Budget or Cost Anomaly Detection, and put the early-delete
   rate in the cost forecast.
5. **Housekeeping rules.** With versioning on, a delete only adds a delete marker; add
   `noncurrent_version_expiration` and `abort_incomplete_multipart_upload` so deleted data truly
   stops billing.

```hcl
rule {
  id     = "archive-sold-listing-photos"
  status = "Enabled"

  transition {
    days          = 120               # past the 90-day minimum; was 30
    storage_class = "GLACIER"
  }
  noncurrent_version_expiration { noncurrent_days = 30 }
  abort_incomplete_multipart_upload { days_after_initiation = 7 }
}
# Alternative: storage_class = "INTELLIGENT_TIERING" at day 0, no early-delete fee.
```

Recommendation: Intelligent-Tiering for anything a seller can still ask to delete, with the
deletion job from point 3, and Glacier only for data that is truly cold and not subject to deletion
requests.
