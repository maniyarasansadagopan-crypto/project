# B0 — The `count` trap

## What `terraform plan` shows

`aws_s3_bucket.landlord_media` uses `count`, so Terraform addresses each bucket by its **position**
in `var.landlord_accounts`: `[0]=la-001, [1]=la-002, [2]=la-003, [3]=la-004`. State is keyed by
those addresses, not by account ID.

I removed `"la-002"` from the list and ran `terraform plan -refresh=false` against the seeded
state. The plan did not say "destroy la-002's bucket". It said:

```
# aws_s3_bucket.landlord_media[1] must be replaced     (haven-media-la-002 -> haven-media-la-003)
# aws_s3_bucket.landlord_media[2] must be replaced     (haven-media-la-003 -> haven-media-la-004)
# aws_s3_bucket.landlord_media[3] will be destroyed    (because index [3] is out of range for count)
Plan: 4 to add, 0 to change, 3 to destroy.
```

(4 to add includes `listing_media` and its lifecycle configuration from `lifecycle.tf`; the
landlord-bucket part is 2 replaced + 1 destroyed.)

Everything after the removed element shifts down one index. Terraform sees `[1]` now wants the name
`haven-media-la-003` instead of `haven-media-la-002`. A bucket name cannot be changed in place, so it
plans destroy-and-recreate. The same happens at `[2]`, and the now-out-of-range `[3]` is destroyed.

## Why it is dangerous here

- **Wrong blast radius.** We meant to remove one landlord's bucket. The plan touches three: la-002,
  la-003 and la-004. Two landlords who did nothing have their buckets destroyed and re-created.
- **These buckets hold customer data.** They are landlord media buckets. A replacement is a
  destroy followed by an empty new bucket, so la-003 and la-004's objects are gone unless the
  bucket is emptied elsewhere first. With `force_destroy = true` that is silent data loss; with the
  default `false`, the apply fails midway on `BucketNotEmpty` and leaves a half-applied state.
- **Naming collisions.** Bucket names are globally unique. The plan creates `haven-media-la-003` at
  `[1]` while the old `haven-media-la-003` at `[2]` still exists, so ordering can fail or race.
- **Billing/tagging drift.** `landlord_account_id` tags are rewritten in place of the old owner, so
  cost attribution is wrong in the window between destroy and recreate.
- **It looks routine.** A one-line list edit produces a large diff that is easy to approve unread.

## The fix

Key resources by **identity**, not position, using `for_each`:

```hcl
resource "aws_s3_bucket" "landlord_media" {
  for_each = toset(var.landlord_accounts)
  bucket   = "haven-media-${each.key}"
  tags     = { landlord_account_id = each.key }

  lifecycle { prevent_destroy = true }
}
```

Addresses become `landlord_media["la-001"]`, `["la-002"]`, and so on, so removing `la-002` affects only
`["la-002"]`.

Migrating the existing state without recreating anything, using `moved` blocks (Terraform 1.1+):

```hcl
moved { from = aws_s3_bucket.landlord_media[0]  to = aws_s3_bucket.landlord_media["la-001"] }
moved { from = aws_s3_bucket.landlord_media[1]  to = aws_s3_bucket.landlord_media["la-002"] }
moved { from = aws_s3_bucket.landlord_media[2]  to = aws_s3_bucket.landlord_media["la-003"] }
moved { from = aws_s3_bucket.landlord_media[3]  to = aws_s3_bucket.landlord_media["la-004"] }
```

(or `terraform state mv` per resource). After the move, `terraform plan` should show **no changes**;
then removing `la-002` shows exactly one destroy. `prevent_destroy` is a second safety net so even
that destroy needs a deliberate, reviewed override. If la-002's data must be kept, use a `removed`
block with `lifecycle { destroy = false }` to drop it from state without deleting the bucket.
